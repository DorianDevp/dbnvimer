OVERVIEW                                                *dbclient-overview*

DBClient.nvim is a Lua plugin backed by a Rust daemon. The UI lives entirely in
normal Neovim buffers: an object sidebar, query buffers, result grids, editable
data buffers, DDL buffers and plan trees.

The guiding idea is that Neovim already knows how to edit text. A data buffer is
therefore a modifiable buffer, not a widget: `ciw`, `<C-v>`, `:%s/`, macros,
`dd`, `o` and `u` all work, and `:w` translates whatever the buffer now says
into the SQL needed to get the database there.

Supported backends: MariaDB/MySQL, PostgreSQL and SQLite.

The Rust core runs as one long-lived process hosting many sessions. That is what
makes real session transactions, server-side statement cancellation and
non-blocking queries possible.

==============================================================================
SETUP                                                   *dbclient-setup*

With lazy.nvim: >

  {
    "DorianDevp/dbnvimer",
    build = "cargo build --release --manifest-path rust/dbclient-core/Cargo.toml",
    opts = {},
  }
<
`opts = {}` is enough to start. DBClient scans the project for databases it can
already reach before you configure anything: `.env` files, `docker-compose.yml`
services, `config/database.yml`, and a project-local `.dbclient.lua` (which is
gated behind the same trust prompt Neovim uses for `exrc`).

Full options: >

  require("dbclient").setup({
    core = { command = nil, statement_timeout_ms = nil },
    ui = {
      sidebar_width = 38,
      result_height = 14,
      max_cell_width = 48,
      preview_limit = 200,
      query_limit = 5000,
      null_display = "∅",
      bool_display = { "true", "false" },
      row_stripes = true,
      winbar = true,
      virtual_fk = true,
      sticky_header = true,
    },
    keys = true,
    detect = { enabled = true },
    store = { enabled = true },
    history = { enabled = true, limit = 1000 },
    guard = {
      confirm_unfiltered_writes = true,
      confirm_destructive = true,
    },
    codegen = {},
    connections = {},
  })
<
Set `vim.g.dbclient_leader` to change the global prefix from `<leader>d`.

Statusline component for lualine and friends: >

  require("dbclient").statusline()
<
==============================================================================
CONNECTIONS                                             *dbclient-connections*

Connections come from three places, in this order of precedence:

    1. `setup()`   read-only, owned by your Neovim config
    2. the store   editable from inside the client
    3. detected    read-only suggestions found in the project

Manage them without leaving Neovim with `<leader>dC` or |:DBClientConnections|.
The manager edits a connection as text in a buffer; `:w` saves it to
`stdpath("data")/dbclient/connections.json`, which is created with mode 0600.

                                                        *dbclient-passwords*
Passwords are never written to that file. A connection names where its secret
comes from instead:

    `password`          a literal value (only sensible in `setup()`)
    `password_env`      the name of an environment variable
    `password_cmd`      a shell command whose first output line is the password
    `password_prompt`   ask once per Neovim session and keep it in memory

Connection fields: >

  {
    adapter = "postgres",       -- mariadb | postgres | sqlite
    host = "127.0.0.1",
    port = 5432,
    user = "app",
    database = "shop",
    path = "~/notes.db",        -- sqlite only
    access = "write",           -- write | read | sandbox
    color = "red",              -- paints the winbar of every bound buffer
    statement_timeout_ms = nil,
    ssh = {
      host = "bastion",         -- a Host alias from ~/.ssh/config works
      user = nil,
      port = nil,
      identity_file = nil,
      jump = nil,               -- ProxyJump chain
    },
  }
<
Several connections can be open at once. The sidebar lists every configured
connection and marks the open ones; `<leader>ds`, the data buffers and the query
buffers each remember which connection they belong to.

==============================================================================
SAFETY                                                  *dbclient-safety*

Running the right statement against the wrong database is the failure that
matters, so:

- A connection with a `color` paints the winbar of every buffer bound to it.
- `access = "read"` is enforced inside the Rust core, so a UI bug cannot get
  around it.
- `access = "sandbox"` runs writes inside a transaction that is always rolled
  back, reporting what would have changed.
- `DELETE` and `UPDATE` without a `WHERE`, and `DROP`/`TRUNCATE`, appear as
  |vim.diagnostic| entries while you type and need confirmation before running.
- Writes from a data buffer carry the values they were based on, so an `UPDATE`
  that would silently overwrite someone else's change fails instead.
- A data buffer without a primary key is read-only.

                                                        *:DBClientLocks*
:DBClientLocks          Who is blocking whom.

                                                        *:DBClientSearch*

                                                        *:DBClientHistory*

                                                        *:DBClientLog*
:DBClientLog            Statements run in this Neovim session, with timings.

                        Index usage counters and unused index candidates.

                                                        *:DBClientWatch*

                        Re-run a statement on a timer, highlighting the cells

                                                        *:DBClientProfile*

                        the connections by identical answers.

                        foreign key metadata.

                                                        *:DBClientImport*

                        confirmed with `:w`.

                        a re-run replaces it rather than stacking another.

                                                        *:DBClientCompare*
:DBClientCompare        Diff the current result set against a saved snapshot.

                                            *:DBClientWorkspaceRestore*

                        Reopen everything the saved workspace describes.

DATA BUFFER

The data buffer is a normal modifiable buffer. Edit cells the way you edit
any text: `ciw`, visual block, `:%s/old/new/g`, macros, `dd` to delete a
row, `o` to add one. `u` undoes staged changes because it is Neovim's own
undo. Writing the buffer with `:w` turns the difference against the fetched
snapshot into `UPDATE`, `INSERT` and `DELETE` statements, shows them for
confirmation and applies them in one transaction.

Only navigation and inspection are mapped, so nothing shadows an editing
key.

    K                inspect the full cell value
    gK               the whole record: everything related to this row
    gd               follow the foreign key under the cursor
    gU               open the rows that reference this one
    gu               list referencing rows in the quickfix
    g[               back along the navigation trail
    g]               forward along the navigation trail
    gb               jump to any point on the trail
    gs               statistics for this column
    gS               sort by this column
    gf               filter rows with a WHERE expression
    gF               clear the filter and sort
    gt               transposed view of this row
    gh               hide this column
    gH               show all columns
    gn               set this cell to SQL NULL
    gy               yank cell, row or selection as...
    gp               duplicate this row as a new INSERT
    gx               extract this row plus everything it needs
    gr               reload from the database
    gD               open the DDL for this table
    gG               generate code from this table
    gI               import a CSV into this table
    ge               export this table
    ]c               next cell
    [c               previous cell
    ]r               next row
    [r               previous row
    ]p               next page
    [p               previous page
    g?               show this help

RECORD

One row with everything the schema says is connected to it: the row itself,
the row behind every foreign key it holds, and a sample of every row that
points back at it. Each section is a fold, so `zo`, `zc` and `zR` do what
they always do.

    <CR>             open this table, filtered to these rows
    gu               reveal masked values
    gr               fetch the record again
    q                close the record
    g?               show this help

STATEMENT WORKLOAD

Every statement the *server* has run, aggregated by it and ranked by total
time rather than by average — which is what finds the query that takes
four milliseconds eighty thousand times an hour. Snapshots compare against
it later, so "this got eleven times slower" is a fact rather than a feeling.

    <CR>             open it in a query buffer to fill in the parameters
    gy               yank the statement
    s                save the current counters
    c                compare against a saved snapshot
    gr               read the counters again
    q                close
    g?               show this help

DDL BUFFER

The object's `CREATE` statement as text. Edit it and `:w` to see the
migration DBClient would run; nothing reaches the server until you confirm.

    gr               reload the DDL from the server
    gD               diff against the server version
    q                close the buffer
    g?               show this help

==============================================================================
DATA BUFFERS                                            *dbclient-data*

A data buffer is a modifiable buffer holding a rendered grid: >

  shop.customers  ·  rows 1-200 of 4123  ·  order by id asc
  id  | name    | city | note
  ----+---------+------+-----------
  1   | Łódź    | PL   | ∅
  2   | NULL    | DE   | literal null
<
`∅` is a SQL NULL; the literal text `NULL` renders as itself, and both survive a
round trip through the buffer. Values containing a newline, a tab or the column
separator are escaped as `\n`, `\t` and `\|` so a row is always exactly one
line, and unescaped on write.

Column widths are measured in display cells, so multibyte text lines up. A value
too wide to show is truncated with `…`, and editing a truncated cell is refused
rather than silently shortening the stored value — use `K` to edit the whole
value instead.

Row identity is tracked with extmarks and reconciled against the primary key, so
reordering rows, deleting lines and line-wise edits still attribute each change
to the right record.

`:w` collects the difference against the fetched snapshot, shows both a summary
and the exact SQL — generated by the same code that will run it — and applies
everything in one transaction after you confirm.

==============================================================================
QUERY BUFFERS                                           *dbclient-query*

A query buffer is a real `sql` buffer, so treesitter, snippets and your own
mappings apply.

Statements are split by the Rust core, which understands string literals, `--`
and `/* */` comments (nested), PostgreSQL dollar quoting and MySQL's
`DELIMITER`. A semicolon inside a string or a stored procedure body does not
split a statement.

                                                        *dbclient-conn-header*
A header binds a `.sql` file to a connection: >

  -- @conn: staging
  select * from orders limit 10;
<
This makes a directory of per-environment queries something you can keep in the
repository.

`K` describes the table or column under the cursor from the cached schema, and
`gd` opens its DDL. Completion is available through 'omnifunc', and an
`nvim-cmp` source is registered automatically when cmp is installed.

Server errors and static problems appear as |vim.diagnostic| entries, so `]d`
and `[d` navigate them and your usual diagnostic UI shows them.

==============================================================================
SSH TUNNELS                                             *dbclient-ssh*

Add an `ssh` table to a connection and DBClient opens a local forward before
connecting: >

  ssh = {
    host = "bastion",           -- or a Host alias from ~/.ssh/config
    user = "deploy",
    identity_file = "~/.ssh/id_ed25519",
    jump = "jump.example.com",  -- ProxyJump
  }
<
The local port is chosen automatically and retried if it is taken. DBClient
waits for the forward to accept connections rather than guessing with a sleep,
keeps the `ssh` child process for the lifetime of the tunnel (so shutting it
down does not depend on a possibly recycled pid, and works on Windows), and
passes `BatchMode=yes` and `ConnectTimeout` so a tunnel fails fast instead of
hanging on a prompt.

`remote_host` and `remote_port` default to the connection's own host and port.

==============================================================================
HEALTH                                                  *dbclient-health*

>
  :checkhealth dbclient
<
Checks the Neovim version, that `ssh` is on `PATH`, that the core binary exists
and runs, that its protocol version matches the plugin's, that the daemon
answers, that every configured connection is valid, and that the connection
store has restrictive permissions.
